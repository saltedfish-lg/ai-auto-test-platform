# Engineering Autonomy

## 核心规则

冻结基线约束“已定义事实”，不是完整实现白名单。

遇到未定义事项时判断：

- A：是否改变用户可观察行为？
- B：是否改变业务规则或状态语义？
- C：是否改变 API / 数据 / 事件契约？
- D：是否改变权限或安全边界？
- E：是否改变跨模块职责、并发、锁、租约、恢复语义？

A-E 任一为“是” → 产品级未决事项：不得自行创造规则；报告问题、影响、唯一推荐方案和备选方案，暂停该未决语义。

A-E 全部为“否” → 工程实现事项：Codex 有自主技术决策权，应基于现有代码、项目技术栈、可维护性、可测试性、最小复杂度直接设计并实现，不得因文档未明确而默认停工。

## 可以自主决定

- 内部目录/模块/类/函数/私有方法拆分；
- Repository / Service / Mapper / Composable / Store 的内部组织；
- Grid/Flex、Element Plus 组件组合、非产品语义视觉细节；
- 成熟维护库的具体选择（满足冻结算法/协议/安全参数）；
- 日志位置和结构化字段（不得泄密、不得改变审计契约）；
- 测试 fixture、builder、helper；
- 不改变唯一性/业务语义的索引和查询优化；
- 可逆的代码重构和重复代码抽取。

## 必须升级

- 新增/删除业务状态或状态转换；
- 新增公开 API、DTO 字段、权限码、错误码、事件；
- 改变登录、重试、恢复、删除、归档、审核、并发策略；
- 改变 Runner 租约/资源冲突/任务迁移语义；
- 改变数据所有权、跨模块职责或安全边界；
- 把“现有契约冲突”自行解释成新的产品规则。
