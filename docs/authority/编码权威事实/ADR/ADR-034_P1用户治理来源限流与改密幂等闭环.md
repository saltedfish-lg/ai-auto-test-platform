# ADR-034：P1用户治理、来源限流与改密幂等闭环

## 状态

ACCEPTED / CURRENT LIVING AUTHORITY

## 决策范围

本ADR承接已由用户确认并同步到当前 Living Authority 的三个P1治理决策：

- `GOV-P1-002 / SYSTEM_GENERATED_ONE_TIME_TEMP_CREDENTIAL`；
- `GOV-P1-003 / SOURCE_RATE_LIMIT_ENABLED_MYSQL84`；
- `GOV-P1-005 / PASSWORD_CHANGE_REVOKES_REFRESH_SESSIONS_AND_REAUTHENTICATES`。

产品响应、权限、错误码、状态和验收语义以 Authentication Contract、OpenAPI、Permission Closure 与 Acceptance Closure 为准；本ADR只固定长期技术边界。

## 模块与状态Owner

1. HTTP Adapter只解析请求与组装响应；Application Command Coordinator只编排同一工作单元，不取得领域状态写权。
2. UserAggregateService独占`atp_user`生命周期写权；CredentialService独占平台凭据、凭据版本和临时密码生成/Hash；SessionService独占Refresh Session状态。
3. AuthorizationService只使用`atp_user_role_binding`与`atp_data_scope_grant`作为认证授权事实，不得使用`atp_role_binding`或`atp_user.role_binding_id`建立平行RBAC模型。
4. AuthenticationRateLimitService独占`atp_auth_source_rate_limit`；AuthenticationAuditService只追加写`atp_auth_security_audit`。

## 部署共享HMAC主秘密

1. 所有API实例必须通过`ATP_AUTH_HMAC_MASTER_KEY_FILE`加载同一严格JSON Key Ring；缺失、不可读、为空、格式无效或实例间不一致时启动失败关闭。根字段固定为`ring_version/active_key_id/keys`；每个key使用至少32字节的base64url材料及UTC生命周期时间。
2. 使用HKDF-SHA256和独立domain label派生来源限流、改密请求指纹、幂等存储键；不得复用JWT、Bootstrap或数据库秘密。
3. 主秘密与派生密钥不得记录、回显、持久化或进入对象默认`repr`。轮换重叠至少覆盖24小时幂等保留期，滚动部署期间所有实例必须接受同一有效密钥集合。

## MySQL来源固定窗口

1. Login与Refresh在密码Hash、Token或Session校验前，以独立短事务消费MySQL 8.4共享固定窗口；窗口长度300秒，阈值分别为60与300。
2. 来源IP以直接peer为默认事实。只有直接peer命中`ATP_TRUSTED_PROXY_CIDRS`时才解析受信代理链；规范化IP经HMAC后持久化，原始IP不得入限流表。
3. 复合唯一键上的原子插入/行锁递增负责多实例串行化，计数封顶在拒绝哨兵61/301。第61/301次返回429和`Retry-After`；限流状态或拒绝审计事务失败时返回503并禁止继续认证。
4. 已提交计数不随之后的认证失败回滚。过期记录只由受控有界批次清理，不允许在线请求触发无界删除。

## 用户治理与一次性临时凭据

1. 创建用户在一个事务内提交User、Credential、至少一个UserRoleBinding、所需DataScopeGrant、幂等记录及`USER_CREATED/ROLE_ASSIGNED`安全审计。
2. 临时密码使用CSPRNG生成并立即以Argon2id Hash入库；明文只允许存在于首次已提交响应的进程内对象中，不得进入幂等记录、审计、Outbox、日志或可恢复制品。
3. 相同幂等键与相同非秘密指纹重放只返回`ALREADY_DELIVERED`，不得恢复或再次生成临时密码。
4. 普通用户治理与Role Binding命令不新增领域Event/Outbox；仅默认admin初始化复用既有`user.active/admin.active`。`atp_user_role_binding`不得冒充`OBJ-087`发布`role_binding.*`事件。
5. admin不可删除、禁用、锁定、归档、改名、重置凭据或解除`ROLE-SUPER-ADMIN`；服务端事务内保护不得依赖前端隐藏。

## Change Password幂等事务

1. Access JWT必须先完成密码学验证并取得principal，再以principal、operation和外部`Idempotency-Key`派生物理幂等键；请求指纹使用部署共享HMAC覆盖规范化current/new password请求。
2. 首次执行按`IdempotencyRecord -> User -> Credential -> RefreshSession(session_id排序)`加锁，校验当前密码与凭据版本，只递增一次`credential_version/row_version`，撤销全部Refresh Session，写`PASSWORD_CHANGED`审计，并以`response_status=204、response_json=NULL`终结`contract_version=2`记录。
3. 相同键与相同指纹的终态重放在JWT密码学验证后直接返回204，不再次验证旧密码、不重复变更或审计；相同键与不同指纹返回409。
4. 成功响应不创建Session、不签发Token；前端收到204后立即清除内存认证状态并`replace`到登录页。

## 统一锁序、事件与迁移

1. 命令事务统一锁序为：IdempotencyRecord、按`user_id`排序的User、Credential、按`session_id`排序的RefreshSession、按`binding_id`排序的UserRoleBinding，最后插入Audit；禁止跨Owner旁路写表或拆分业务状态与审计事务。
2. V7只新增共享来源限流表、当前绑定/幂等清理索引、幂等V2兼容字段和认证审计action约束；V3至V6不可修改。
3. V7部署必须排空认证写流量、执行迁移、通过schema capability检查后整体启用新代码；禁止旧写侧与V7写侧混跑，失败采用roll-forward。
4. 旧`contract_version=1`记录保留至自然过期，不反推principal；所有新写显式使用version 2。

## 验证要求

静态契约测试不能替代真实运行证据。最终验证必须覆盖真实MySQL 8.4空库与升级迁移、并发阈值和幂等一次变更、故障回滚、可信/不可信代理链、秘密泄漏扫描，以及真实Chromium中的临时凭据、禁用/锁定、Refresh恢复和改密204重新认证流程。
